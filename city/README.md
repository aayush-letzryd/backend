# City Master (`public.core_cities`) — Knowledge Transfer & Technical Specification

## 1. Overview & Business Purpose

`public.core_cities` is the master source of truth for all operational and inactive cities in the LetzRyd platform. All geographical routing, pricing zones, partner allocations, hub operations, and ride dispatch services reference this table.

---

## 2. Table Schema Definition

```sql
CREATE TABLE public.core_cities (
    city_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    city_code VARCHAR(10) NOT NULL UNIQUE,
    city_name VARCHAR(100) NOT NULL UNIQUE,
    state VARCHAR(100) NOT NULL,
    country VARCHAR(100) NOT NULL DEFAULT 'India',
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by INTEGER NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by INTEGER NULL
);
```

### Data Dictionary

| Column Name | Data Type | Nullable | Default | Description |
| :--- | :--- | :--- | :--- | :--- |
| `city_id` | `INTEGER` | **No** | Identity (1, 2, ...) | Primary key, uniquely identifies each city record. |
| `city_code` | `VARCHAR(10)` | **No** | *None* | Short, uppercase business identifier (e.g., `BLR`, `HYD`, `MUM`). Must be unique across the platform. |
| `city_name` | `VARCHAR(100)` | **No** | *None* | Official unique name of the city (e.g., `Bangalore`, `Hyderabad`, `Mumbai`). |
| `state` | `VARCHAR(100)` | **No** | *None* | State/province in which the city is located. |
| `country` | `VARCHAR(100)` | **No** | `'India'` | Country name. |
| `is_active` | `BOOLEAN` | **No** | `TRUE` | Operational flag. `TRUE` = active/operational; `FALSE` = deactivated/historical. |
| `created_at` | `TIMESTAMPTZ` | **No** | `CURRENT_TIMESTAMP` | System timestamp when city record was registered. |
| `created_by` | `INTEGER` | **Yes** | `NULL` | Portal user identifier who created the record (`NULL` for automated/system seed). |
| `updated_at` | `TIMESTAMPTZ` | **No** | `CURRENT_TIMESTAMP` | System timestamp when the record was last modified (auto-updated by trigger). |
| `updated_by` | `INTEGER` | **Yes** | `NULL` | Portal user identifier who made the last change. |

## 3. Database Triggers & Guardrails

### 3.1. Automatic `updated_at` Refresh
- **Trigger**: `trg_core_cities_set_updated_at` (`BEFORE UPDATE`)
- **Function**: `public.core_set_city_updated_at()`
- **Mechanism**: Automatically sets `NEW.updated_at = CURRENT_TIMESTAMP` whenever an `UPDATE` statement is executed on `core_cities`.

### 3.2. Physical Deletion Prevention
- **Trigger**: `trg_core_cities_prevent_delete` (`BEFORE DELETE`)
- **Function**: `public.core_prevent_city_delete()`
- **Mechanism**: Raises a PostgreSQL exception (`RAISE EXCEPTION`) if an SQL `DELETE` is attempted. 
- **Reason**: Cities are parent references to rides, transactions, vehicles, drivers, and hubs. Physical deletion causes catastrophic relational breakage. All deletions must be soft-deletions (`is_active = FALSE`).

## 5. Portal Integration & Future Flow

When building the Admin / Management Portal, the backend services must adhere to the following contracts:

### 5.1. Add City Flow
- **User Action**: Admin inputs City Code, City Name, State, Country.
- **Backend API**: `POST /api/v1/cities`
- **Request Payload**:
  ```json
  {
    "city_code": "DEL",
    "city_name": "Delhi",
    "state": "Delhi",
    "country": "India"
  }
  ```
- **Backend SQL**:
  ```sql
  INSERT INTO public.core_cities (city_code, city_name, state, country, created_by, updated_by)
  VALUES ($1, $2, $3, $4, $current_user_id, $current_user_id)
  RETURNING *;
  ```
- **Audit Trigger Result**: Logs a new entry in `core_city_logs` with `action = 'CREATE'`.

---

### 5.2. Edit City Flow
- **User Action**: Admin updates State, Name, or metadata.
- **Backend API**: `PUT /api/v1/cities/:city_id`
- **Request Payload**:
  ```json
  {
    "city_name": "Bengaluru",
    "state": "Karnataka"
  }
  ```
- **Backend SQL**:
  ```sql
  UPDATE public.core_cities
  SET city_name = $1, state = $2, updated_by = $current_user_id
  WHERE city_id = $3
  RETURNING *;
  ```
- **Audit Trigger Result**: Logs an entry in `core_city_logs` with `action = 'UPDATE'`, capturing `old_data` and `new_data`.

---

### 5.3. Deactivate / "Delete" City Flow
- **User Action**: Admin clicks "Delete City" button on the portal.
- **Portal Rule**: **NEVER** issue an SQL `DELETE FROM core_cities WHERE city_id = $1`.
- **Backend API**: `DELETE /api/v1/cities/:city_id` (or `PATCH /api/v1/cities/:city_id/deactivate`)
- **Backend SQL**:
  ```sql
  UPDATE public.core_cities
  SET is_active = FALSE, updated_by = $current_user_id
  WHERE city_id = $1
  RETURNING *;
  ```
- **Audit Trigger Result**: The audit trigger detects `is_active: TRUE -> FALSE` and automatically records `action = 'DELETE'` in `core_city_logs`.

## 6. Future Schema Extensions (Foreign Keys)

Once `core_portal_users` is created, foreign keys should be attached as:

```sql
ALTER TABLE public.core_cities
    ADD CONSTRAINT fk_core_cities_created_by
    FOREIGN KEY (created_by)
    REFERENCES public.core_portal_users(portal_user_id);

ALTER TABLE public.core_cities
    ADD CONSTRAINT fk_core_cities_updated_by
    FOREIGN KEY (updated_by)
    REFERENCES public.core_portal_users(portal_user_id);
```
